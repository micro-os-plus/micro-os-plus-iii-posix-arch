# Preemption and SMP on the synthetic POSIX port — design plan

Status: proposal, not implemented. Written 2026-10-01.

## Goal

The synthetic POSIX port currently runs the µOS++ scheduler in cooperative
(non-preemptive) mode only. The long-term goal is SMP support in the RTOS
scheduler; preemption is the first step towards it.

This document records the analysis of the current implementation, why it
cannot be extended to SMP, and the proposed replacement design, so that
later work can refer to it.

## Platform scope

The port must run on:

| OS | x86_64 | aarch64 | riscv64 |
| --- | --- | --- | --- |
| GNU/Linux | yes | yes | yes |
| macOS | yes | yes (Apple Silicon) | n/a |

Windows is out of scope; it will get a separate port. The kernel-side
port API must therefore not assume POSIX signals (see
[Kernel changes](#kernel-changes-required-for-smp)).

Design constraints derived from this scope:

- No architecture-specific code (no assembly, no `mcontext` access); all
  architecture differences must be absorbed by POSIX/C++ APIs.
- Only POSIX features available on **both** macOS and GNU/Linux may be
  used, or the differences must be confined to small `__APPLE__` /
  `__linux__` blocks (see [Platform-specific notes](#platform-specific-notes)).

## Current implementation

- Each µOS++ thread is a `ucontext` built on the thread's µOS++ stack
  (`port::context::create()`), using either the native POSIX functions or
  libucontext (`OS_INCLUDE_LIBUCONTEXT`, `libucontext_posix_*` variants).
- All µOS++ threads run on a single host thread.
- "Interrupts" are the `SIGALRM` signal, generated by
  `setitimer(ITIMER_REAL)` at `OS_INTEGER_SYSTICK_FREQUENCY_HZ`.
- Critical sections block/unblock `SIGALRM` with `sigprocmask()`.
- `signal_nesting` (global) tracks handler mode; `lock_state` (global) is
  the scheduler lock.
- `port::scheduler::reschedule()` performs the context switch with
  `swapcontext()` (or `setcontext()` for terminated threads).

### Why it is cooperative

The core already supports preemption: `os_systick_handler()` calls
`port::scheduler::reschedule()` at the end of every tick, and
`scheduler::preemptive()` / `OS_BOOL_RTOS_SCHEDULER_PREEMPTIVE` exist.

The POSIX port simply ignores the call when made from the handler:

```cpp
if (rtos::scheduler::locked () || rtos::interrupts::in_handler_mode ())
  return;
```

On Cortex-M, `reschedule()` only pends PendSV and the switch occurs on
exception return. The POSIX port has no PendSV equivalent; this is the gap.

## Option A — preemption on top of ucontext (rejected for SMP)

### Mechanism

1. In handler mode, `reschedule()` sets a `reschedule_pending` flag instead
   of returning (the equivalent of Cortex-M `is_reschedule_pending`).
2. At the end of `systick_clock_signal_handler()`, decrement
   `signal_nesting` (it is global and must not leak into the next thread),
   then, if preemptive, not locked and pending, call `swapcontext()` while
   `SIGALRM` is still blocked by the handler mask.
3. When the preempted thread is resumed, `swapcontext()` returns inside the
   handler, the handler returns, and the kernel `sigreturn` restores the
   interrupted registers. The signal frame stays on the thread's own stack.
4. Optionally also check the pending flag in `critical_section::exit()` and
   `scheduler::unlock()`, to mimic PendSV firing when interrupts are
   re-enabled.

Estimated size: 100–200 lines, mostly in `src/rtos/os-core.cpp`.

### Problems

| Issue | Severity | Mitigation |
| --- | --- | --- |
| libc is not reentrant across switches: a thread preempted inside `malloc`/`printf`/trace holds a libc lock owned by the single host thread; the next thread taking it deadlocks (glibc) or aborts (macOS `os_unfair_lock`). | High | Lock the scheduler (or block the signal) around port libc calls (trace, default allocator); document the risk for application code. |
| `swapcontext`/`setcontext` from a signal handler is undefined behaviour in POSIX. | Medium (formal) | Works in practice with glibc and libucontext. |
| The signal mask must travel with each context. | Medium | Keep the `libucontext_posix_*` variants; in `context::create()` explicitly clear `SIGALRM` from `uc_sigmask`, since `getcontext()` copies the mask active at creation time. |
| Signal frames on thread stacks (larger on aarch64 Linux with SVE). | Low | The 32 KiB minimum is sufficient. |
| Blocking system calls still block the whole process. | Unchanged | — |

### Why it does not extend to SMP

Simulating N cores requires N host threads executing µOS++ code in
parallel. With ucontext this means N carrier pthreads switching µOS++
contexts (an M:N model). As soon as a µOS++ thread migrates between
carriers:

- **Thread-local storage does not migrate.** `swapcontext()` does not
  save the TLS register (`fs` on x86_64, `tpidr_el0` on aarch64), and the
  compiler may cache the address of `errno` or other `thread_local` data
  across the switch. The resumed thread then accesses another thread's TLS.
- **libc locks are owned by host threads.** A lock taken on carrier A and
  released on carrier B is undefined behaviour; macOS aborts.
- **ThreadSanitizer does not work** with ucontext switches, and TSan is the
  most valuable host-side tool for validating SMP kernel locking.

Pinning µOS++ threads to carriers avoids these problems but removes
migration, which defeats the purpose of SMP.

## Other alternatives considered

| Option | Verdict |
| --- | --- |
| Native `ucontext` | Deprecated, removed from POSIX.1-2008; glibc performs a `sigprocmask` system call on every switch; availability on macOS arm64 not verified. |
| libucontext (current) | Small, portable, consistent; fine for the single-core cooperative port. |
| Hand-written assembly switch (Boost.Context `fcontext` style) | Fastest, but 5 ABI variants (x86_64/aarch64 on Linux and macOS, riscv64 on Linux) to maintain, and it has the same TLS/libc problems. |
| `sigsetjmp`/`siglongjmp` + `sigaltstack` (GNU Pth) | Fragile; rejected by glibc `_FORTIFY_SOURCE` checks. |
| **One host pthread per µOS++ thread** (FreeRTOS POSIX/Linux port style) | **Selected.** |

## Option B — one host pthread per µOS++ thread (selected)

### Principle

Each µOS++ thread is a real host pthread. At most N of them (one per
simulated core) are allowed to run at any time; all others are parked.
A context switch is a hand-off between pthreads. The host OS handles
migration, so TLS and libc lock ownership remain correct, and debuggers,
ASan and TSan see real threads.

This design uses only pthreads, signals and C++ atomics, so it contains no
architecture-specific code and works unchanged on x86_64, aarch64 and
riscv64.

### Per-core state

For each simulated core:

- `id`;
- `current_thread`;
- interrupts-disabled state;
- `signal_nesting` (replaces the current global);
- `reschedule_pending`;
- scheduler lock state (replaces the current global `lock_state`).

The current core is found from the running pthread (e.g. a `thread_local`
pointer set when a thread is dispatched on a core).

### Threads and stacks

- Each µOS++ thread is created as a pthread with
  `pthread_attr_setstack()` on the µOS++ stack, so stack size accounting
  and stack checks keep working (allow headroom for signal frames and
  the pthread internal structures). The size and alignment constraints
  differ per platform; see
  [Platform-specific notes](#platform-specific-notes).
- A newly created thread starts parked and runs only when dispatched.
- Thread termination/destruction must exit and reclaim the pthread
  properly (`pthread_exit()` from the thread, join/detach from the
  scheduler side), replacing the current `setcontext()` path.

### Parking and hand-off

- A parked thread waits in `sigsuspend()` for a dedicated `SIG_RESUME`
  signal. `sigsuspend()` is async-signal-safe, so parking is also valid
  from within a signal handler.
- Context switch on a core: the outgoing thread sends
  `pthread_kill(next, SIG_RESUME)` and then parks itself in
  `sigsuspend()`.
- `pthread_kill()` is async-signal-safe, so the whole preemption path uses
  only functions allowed in signal handlers (unlike Option A).
- Care must be taken with the race between waking the next thread and
  parking the current one; the resume signal must be blocked before the
  hand-off and unblocked atomically by `sigsuspend()`.
- Condition variables and unnamed semaphores are avoided in the signal
  path (and `sem_init()` is not supported on macOS).

### Interrupts and critical sections

- *Local interrupt disable* (per core) = `pthread_sigmask()` on the thread
  currently running on that core, blocking the tick and IPI signals.
  This gives real per-core semantics. The current `sigprocmask()` calls
  must be replaced, since its behaviour in a multi-threaded process is
  unspecified by POSIX.
- All port signals must be blocked by default in every host thread (set
  the mask in the creating thread before `pthread_create()`, so it is
  inherited), and only unblocked where intended. Signals must always be
  sent to a specific thread with `pthread_kill()`; process-directed
  signals (such as the current `setitimer()`/`SIGALRM`) can be delivered
  to any thread that does not block them.
- *Cross-core kernel lock* = spinlock based on `std::atomic` (lock-free
  atomics are safe in signal handlers).
- Kernel critical section = local interrupt disable + kernel spinlock.

### Tick and preemption

- A dedicated timer pthread generates the ticks. macOS lacks both
  `timer_create()` and `clock_nanosleep()`, so the portable choice is a
  loop that computes the next deadline from `clock_gettime(CLOCK_MONOTONIC)`
  and sleeps the remaining interval with `nanosleep()`, tracking absolute
  deadlines to avoid cumulative drift. On Linux, `clock_nanosleep()` with
  `TIMER_ABSTIME` may be used in a `__linux__` block.
- On each tick it sends `pthread_kill(SIG_TICK)` to the thread running on
  each core (or only on core 0, with the others receiving IPIs, depending
  on the chosen kernel design).
- The `SIG_TICK` handler enters handler mode for that core, calls
  `os_systick_handler()`, leaves handler mode, and if a reschedule is
  pending and allowed, performs the hand-off and parks in `sigsuspend()`.
  When resumed it returns from the handler normally.

### Inter-processor interrupts

- Rescheduling another core = set that core's `reschedule_pending` and send
  `pthread_kill(SIG_IPI)` to the thread running on it.
- The IPI handler behaves like the tick handler without the clock update.

### Idle

- Each core has its own idle thread; `wait_for_interrupt()` parks the idle
  thread until a tick or IPI arrives (`sigsuspend()` with the relevant
  signals unblocked, replacing `pause()`).

### Remaining libc hazard

A thread suspended while holding a libc lock no longer corrupts state.
Another thread needing the same lock blocks in the host and keeps its core
busy; a deadlock occurs only if all cores are blocked this way. The port's
own trace and allocator calls should still block the preemption signals
around libc calls.

### Costs

- A context switch costs microseconds instead of nanoseconds; irrelevant
  for a simulator.
- Signal numbers: three signals are needed (`SIG_TICK`, `SIG_IPI`,
  `SIG_RESUME`); real-time signals are not available on macOS, so use
  `SIGALRM`/`SIGUSR1`/`SIGUSR2` or similar, and document them as reserved.
- Execution is non-deterministic between runs.

## Platform-specific notes

### Stacks

- **Minimum size.** Linux requires at least `PTHREAD_STACK_MIN`, which is
  architecture dependent and, since glibc 2.34, not a constant; query
  `sysconf(_SC_THREAD_STACK_MIN)` at run time (on aarch64 it is
  typically 128 KiB, much larger than on x86_64). The effective minimum
  must be the maximum of the µOS++ minimum (currently 32 KiB) and this
  value.
- **Page alignment.** macOS requires the stack address and size passed
  to `pthread_attr_setstack()` to be multiples of the page size, which is
  16 KiB on Apple Silicon and 4 KiB on Intel. Use `sysconf(_SC_PAGESIZE)`,
  and make the µOS++ stack allocation page aligned (e.g. via
  `posix_memalign()` or `mmap()`).
- **Hidden usage.** glibc places the thread descriptor and static TLS at
  the top of a user-supplied stack, so the usable size is smaller than the
  allocated size; stack usage statistics must account for this.
- **Signal frames.** Signal frames are much larger when the architecture
  has wide vector state: aarch64 Linux with SVE/SME, riscv64 Linux with the
  V extension. Add a margin derived from `sysconf(_SC_MINSIGSTKSZ)` (Linux)
  or `MINSIGSTKSZ`/`SIGSTKSZ` (macOS) to the default stack sizes.
- **Guard pages.** With `pthread_attr_setstack()` no guard page is
  created; consider an `mmap()`-ed allocation with a `PROT_NONE` page
  below each stack in debug builds, to turn overflows into a fault.

### Signals

- macOS has no real-time signals; use only the classic signals common to
  both systems: `SIGALRM`, `SIGUSR1`, `SIGUSR2` (and possibly `SIGVTALRM`
  or `SIGPROF`, if not used by profilers). Do not use `SIGRTMIN`, even on
  Linux, to keep a single code path; glibc also reserves some real-time
  signals internally.
- `struct sigaction` field access differs between macOS and Linux (already
  handled in the current port); keep both branches.
- Install handlers with `SA_RESTART` so interrupted system calls in
  application code are restarted.

### Clocks

- Replace `gettimeofday()` in the high-resolution clock with
  `clock_gettime(CLOCK_MONOTONIC)`; it is available on both systems,
  has nanosecond resolution, and is not affected by wall-clock
  adjustments.

### Atomics

- `std::atomic` operations used in signal handlers must be lock-free;
  check with `static_assert(std::atomic<T>::is_always_lock_free)`.
  This holds for 32/64-bit types on x86_64, aarch64 and riscv64
  (RV64GC includes the A extension).
- aarch64 and riscv64 (RVWMO) have weak memory models, unlike x86_64
  (TSO). Code that passes on x86_64 may fail on the others if barriers
  or memory orders are missing; test on all three.

### Debuggers

- The port signals interrupt debugging sessions unless configured:
  - gdb: `handle SIGALRM SIGUSR1 SIGUSR2 nostop noprint pass`;
  - lldb: `process handle SIGALRM SIGUSR1 SIGUSR2 -n false -p true -s false`.
- Document these in `NOTES.md` together with the CodeLLDB launcher.

### Sanitisers

- ASan and TSan are available on Linux x86_64/aarch64 and macOS
  x86_64/arm64. Sanitiser support on Linux riscv64 is more recent and
  less complete (check the GCC/clang version in use); treat it as
  best-effort.
- TSan does not support `pthread_attr_setstack()` stacks perfectly in all
  versions; if false positives appear, verify with plain pthread stacks.

### Linux C libraries

- The primary target is glibc. musl (e.g. Alpine) should work since only
  standard POSIX calls are used, but it is not a primary test target.

## Windows

Windows will get a separate port. To make that possible without
duplicating the kernel work:

- The kernel-side SMP port API (core id, spinlocks, IPI, park/resume,
  local interrupt mask) must be expressed in OS-neutral terms, never in
  terms of signals.
- A Windows port would likely implement the same model with native
  threads, `SuspendThread()`/`ResumeThread()` (or events) for parking
  and preemption, and a timer thread, as in the FreeRTOS Win32 port.
- Keep the POSIX-specific code in this repository; do not add `_WIN32`
  branches here.

## Kernel changes required for SMP

Most of the SMP work is in the portable core
(`micro-os-plus-iii.git`), which currently assumes a uniprocessor:
"interrupts disabled" is the only lock and `scheduler::current_thread_`
is a single global.

- New port API:
  - `port::cpu::id()` and the number of cores;
  - spinlock type and operations;
  - send IPI to a core;
  - per-core `wait_for_interrupt()`.
- Kernel critical sections become local interrupt disable + kernel
  spinlock (start with one big kernel lock).
- Per-core scheduler state: current thread, idle thread, scheduler lock,
  statistics.
- Ready list policy: a single shared list initially; per-core lists later.
- CPU affinity in thread attributes.
- Atomics and memory barriers wherever the kernel relies on interrupts
  being disabled for visibility.
- All hardware ports (Cortex-A/R, RISC-V, aarch64) must implement the new
  port API (trivial single-core versions for existing ports).

Given that µOS++ IIIe is end-of-life, consider implementing the kernel
changes in µOS++ IVe, using this POSIX port as the prototype platform.

## Phased plan

1. **Single-core preemptive pthread port.** Implement Option B with N=1
   and preemption enabled. Keep the existing libucontext implementation
   selectable by a build option, as a reference.
2. **Validation.** Run the existing core tests (`rtos-apis`,
   `mutex-stress`, `cmsis-os-validator`) with N=1, cooperative and
   preemptive, under ASan and TSan. Results must match the current port.
3. **SMP port API with N=1.** Add the new port API to the core and
   implement it in all ports for a single core; a refactor with no
   behaviour change.
4. **N>1 with a big kernel lock.** Enable multiple cores in the POSIX port
   and run the tests under TSan.
5. **Refinement.** Finer-grained locking, CPU affinity, per-core ready
   lists, as needed.

## Testing considerations

- True parallelism on the host makes interleavings non-deterministic and
  failures hard to reproduce.
- An optional deterministic test mode could run all simulated cores on one
  host thread with a seeded scheduling order, giving reproducible
  interleavings. It does not exercise memory ordering, so it complements
  the parallel mode rather than replacing it.
- Test matrix: every phase must pass on all five platforms (Linux x86_64,
  aarch64, riscv64; macOS x86_64, arm64), with GCC and clang where
  available. aarch64 and riscv64 (weak memory ordering) are more likely
  to expose missing barriers than x86_64 (TSO).
- Prefer native riscv64 hardware for testing. QEMU user-mode emulation is
  convenient, but its signal delivery and multi-threading differ from a
  real kernel; use it only for smoke tests, or use QEMU system emulation.
